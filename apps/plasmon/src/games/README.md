# Games

`src/games/` contains Plasmon-owned game content and bootstrap glue. It is not a parallel launcher, emulator shell, or resource-dispatch architecture.

## Architecture

Game resources participate in the same filesystem/opening model as other user resources. Runtime selection belongs to associations and the owning runtime implementation; Shell, Desktop, File Manager, and generic filesystem code do not acquire game-title-specific behavior.

Reusable game runtimes belong under the appropriate native-app/runtime boundary. Game content, metadata, bootstrap/import behavior, and game-specific persistence concerns belong here only when they are genuinely game-domain responsibilities.

Durable emulator progress remains owned by the runtime plus the canonical Plasmon filesystem service. For js-dos, the runtime stores its opaque exported change set by stable game `NodeId`; filename/path changes are presentation changes, not save identity. Browser-local emulator persistence must not become a second Plasmon save database.

## Package and runtime boundaries

Package tier, Demo overlay, and optional runtime selection are independent dimensions:

- Slim remains the constrained package and rejects non-empty optional runtime selection. It contains no Demo games or emulator runtime payloads.
- ordinary Base with no optional runtime selection contains no Demo game resources and no js-dos/EmulatorJS runtime payloads;
- Demo is Base + the explicit Demo overlay and selects the canonical `demo-games` runtime configuration, which selects the same js-dos and EmulatorJS definitions used by custom runtime configurations.

The named Demo package path is:

```text
npm --workspace neutron-plasmon run package:demo
npm --workspace neutron-plasmon run test:package:demo
```

`package:demo` materializes the two user-facing game assets only after the normal Base build. Runtime definitions, versions, pins, caches, and browser transports remain owned by the canonical optional-runtime configuration and runtime consumers rather than being duplicated by Demo content.

## Demo game manifest

`demoGameManifest.ts` is the content manifest below React. It records filesystem destination, expected runtime, immutable source pin, digest, redistribution authority, attribution location, measured bytes, and disposition. Validation fails closed for missing legal/source metadata, duplicate destinations, unknown runtimes, or a required runtime omitted from the selected configuration.

Both games are repository-authored; no commercial or third-party game data is included. The NES title is a deterministic mapper-0/NROM homebrew generated by `demoNesBundle.ts`: it renders a checkerboard and lets the user move a sprite with the directional pad. `demoGameMaterializer.ts` verifies its exact size and digest before writing the Demo-only package asset, so changed generated bytes fail the package build rather than silently changing the approved content. Large Doom-style content is currently omitted. If such content is added later, use a legally redistributable option such as appropriately pinned Freedoom content through the approved optional preparation mechanism; do not add commercial game data or unconditional large payloads to Slim/Base.

## Demo reconciliation and opening

At Demo startup, package-owned game bytes are fetched before service composition and passed to the existing filesystem demo-seed authority. A fresh Demo profile reconciles:

```text
/Games/Plasmon Demo.jsdos
/Games/Plasmon NES Demo.nes
/Games/Plasmon NES Demo - LICENSE.txt
```

The demo-seed ledger remains authoritative, so repeated setup is idempotent and does not accumulate duplicate resources. After reconciliation, neither title has a privileged launch path:

```text
filesystem node
  -> AssociationRegistry (.jsdos or .nes)
  -> OpenService
  -> Process / Windowing
  -> runtime:js-dos or runtime:emulatorjs
```

The selected runtimes are provided by the canonical `demo-games` runtime configuration. Intentionally omitting either required runtime causes manifest/config validation to fail rather than knowingly installing an unusable declared game.

## js-dos Specialist fixture

The explicit packaged-browser js-dos acceptance remains available independently from product Demo through:

```text
?plasmon-fixture=demo-game
```

That compatibility seam loads only the deterministic `Plasmon Demo.jsdos` fixture so js-dos runtime acceptance can exercise normal File Manager opening, real keyboard input, save-before-close, and filesystem-backed restore without depending on product Demo content. The bundle contains a tiny Plasmon-authored DOS program, `dosbox.conf`, and provenance/readme data under GPL-3.0-only.

## Testing

Deterministic game metadata, generator bytes, bootstrap, associations, idempotence, and filesystem -> OpenService -> Process/Window routing are tested below Playwright. Demo package tests verify exact Demo-only fixture inventory, NES digest/size/attribution, both canonical runtime asset inventories, and absence of the test-only EmulatorJS ROM.

Browser verification remains bounded to facts that require an installed browser/runtime: user-facing resources visible in File Manager, real js-dos and EmulatorJS startup, rendered runtime surfaces, and content-specific interaction that lower layers cannot prove. Do not add fixed sleeps, retry inflation, or redundant browser tests per title.
