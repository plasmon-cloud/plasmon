# `.cmd` / `.run` v1 support contract

This document freezes the intended first useful scripting surface for the `experiment/cmd` prototype. It is a product/architecture target, not a claim of GNU/Linux or Bash compatibility.

The defining execution path is:

```text
.cmd
  -> parse shell-like convenience syntax
  -> transpile to readable .run TypeScript
  -> execute with RunContext
  -> CommandRegistry / shell mechanics
  -> production OsApi
  -> real Plasmon authorities
```

`.run` is ordinary TypeScript with an implicit OS runtime context. `.cmd` is the smaller command language for interactive use and straightforward installation/configuration scripts. Complex programming belongs in `.run` rather than growing `.cmd` into a Bash clone.

## v1 `.cmd` syntax

v1 supports:

- whitespace-separated command arguments;
- single-quoted arguments;
- double-quoted arguments;
- backslash escaping for simple literal characters;
- `#` line comments;
- newline-separated command sequencing;
- pipelines with `|`;
- stdout file redirection with `>`;
- relative paths resolved against the shell session's current working directory;
- absolute Plasmon filesystem paths;
- normal command exit status and an explicit `exit` command.

Representative input:

```sh
cd /Documents
cat input.txt | grep Plasmon | sort | uniq > result.txt
open result.txt
```

The generated `.run` remains readable/editable TypeScript, approximately:

```ts
await shell.pipeline([
  commands.cd(["/Documents"]),
]).run();

await shell.pipeline([
  commands.cat(["input.txt"]),
  commands.grep(["Plasmon"]),
  commands.sort([]),
  commands.uniq([]),
]).writeTo("result.txt");

await shell.pipeline([
  commands.open(["result.txt"]),
]).run();
```

## v1 command surface

### Filesystem and navigation

| Command | v1 behavior | Production dependency |
| --- | --- | --- |
| `pwd` | Print session cwd | RunContext/session only |
| `cd` | Change session cwd after validating the target directory | `os.fs.stat()` |
| `ls` | List one directory | `os.fs.list()` |
| `mkdir` | Create a directory | `os.fs.createDirectory()` |
| `cp` | Copy a file/directory using canonical Plasmon semantics | `os.fs.copy()` |
| `mv` | Move/rename using canonical Plasmon semantics | `os.fs.move()` |
| `rm` | Remove using canonical Plasmon user-facing semantics | `os.fs.remove()` |
| `cat` | Read text file(s) or pass stdin through | `os.fs.readText()` when a path is supplied |
| `open` | Open a resource through canonical dispatch | `os.open()` |

`cp`, `mv`, and `rm` must not invent Unix filesystem semantics. They delegate to Plasmon's real copy/move/remove authorities, including collision, protection, Trash, identity, and policy behavior.

### Text and pipelines

| Command | v1 behavior | Production dependency |
| --- | --- | --- |
| `echo` | Write arguments to stdout | RunContext stdout |
| `grep` | Basic text filtering over stdin or a text file | `os.fs.readText()` only for file input |
| `head` | Emit the first N lines, with a small basic option surface | Buffered command layer |
| `tail` | Emit the last N lines; no live-follow mode in v1 | Buffered command layer |
| `wc` | Basic line/word/byte-or-character counting | Buffered command layer |
| `sort` | Basic line sorting | Buffered command layer |
| `uniq` | Filter/count adjacent repeated lines with a small basic option surface | Buffered command layer |
| `tee` | Copy stdin to stdout and one or more files | `os.fs.writeText()` for file outputs |

These are intentionally command/runtime behavior rather than miscellaneous `OsApi` methods.

### OS/session commands

| Command | v1 behavior | Production dependency |
| --- | --- | --- |
| `ps` | Display Plasmon process records in a useful terminal format | `os.processes.list()` |
| `clear` | Clear the visible Terminal surface | Terminal presentation only |
| `history` | Display the current terminal session history | Session state only |
| `help` | List/explain registered v1 commands | CommandRegistry metadata |
| `true` | Return success | Command runtime only |
| `false` | Return failure | Command runtime only |
| `exit` | End/return from the active command/script session with an exit status | RunContext/session only |

### Provisioning

v1 is intended to be capable of scripting a normal base-system installation, not merely manipulating files after everything has already been provisioned.

The target command surface is:

```sh
pkg list
pkg install <package-or-source>
pkg remove <package>
```

These commands must be backed by a truthful production package/application installation authority. They may delegate Plasmon-local package/profile work and Neutron-owned `.neutron` installation to their respective authorities. The scripting layer must not create a second package database or bypass Neutron security/installation ownership.

If the production package authority is not yet ready, package provisioning is a v1 completion blocker rather than something to fake inside `CommandRegistry`.

## v1 production `OsApi` dependency

The v1 scripting layer expects the canonical production API to provide:

```ts
os.fs.stat(path)
os.fs.exists(path)
os.fs.list(path)
os.fs.readText(path)
os.fs.writeText(path, content)
os.fs.createDirectory(path)
os.fs.copy(sourcePath, destinationPath)
os.fs.move(sourcePath, destinationPath)
os.fs.remove(path)

os.open(path)

os.processes.list()
os.windows.list()
```

For base-system provisioning, it additionally expects a truthful package surface equivalent to:

```ts
os.packages.list()
os.packages.install(packageOrSource)
os.packages.remove(packageId)
```

`RunContext`, command registration, cwd, stdin/stdout/stderr, pipelines, redirects, shell history, and Terminal presentation are deliberately **not** part of `OsApi`.

## `.run` v1

`.run` is real TypeScript, not an intermediate DSL. The runtime supplies an implicit context similar to:

```ts
interface RunContext {
  os: OsApi;
  commands: CommandFactory;
  shell: ShellApi;
  args: readonly string[];
  stdin: InputReader;
  stdout: TextWriter;
  stderr: TextWriter;
  signal: AbortSignal;
  print(...values: unknown[]): void;
}
```

A user can therefore graduate from a transpiled `.cmd` into ordinary TypeScript without changing the underlying OS contract:

```ts
if (!(await os.fs.exists("/Documents/result.txt"))) {
  await os.fs.writeText("/Documents/result.txt", "created by .run\n");
}

await os.open("/Documents/result.txt");
```

This is the preferred v1 answer for conditionals, loops, data structures, functions, reusable logic, calculations, and nontrivial error handling.

## Explicitly postponed `.cmd` shell syntax

The following are deliberately outside v1:

| Feature | v1 | Why postponed |
| --- | --- | --- |
| `&&` / `||` | No | Requires compound-command/short-circuit grammar and exit propagation. Useful later, but not needed when `.run` provides explicit control flow. |
| `;` separators | No | Easy enough in isolation, but expands grammar without adding capability beyond newline sequencing. |
| `$VAR` / shell variables | No | Requires an environment/expansion model, quoting rules, scope, and persistence semantics. `.run` already has TypeScript variables. |
| `$()` / backtick substitution | No | Requires nested parsing/execution and careful output/quoting semantics. Medium/high effort. |
| `>>` append redirect | No | Small follow-up, but requires a deliberate append/write API/semantics rather than pretending `writeText()` is append-safe. |
| `<` stdin file redirect | No | Requires more redirect grammar and stream composition. Pipelines plus `cat` cover the main v1 use case. |
| `2>` / fd redirects | No | Requires a general file-descriptor/stdio redirection model. |
| `&` / jobs | No | Requires background lifecycle, jobs table, cancellation, Terminal ownership, and process semantics. High effort. |
| globbing `*` / `?` | No | Requires path expansion rules, escaping, hidden-resource semantics, and deterministic ordering. Medium effort. |
| aliases | No | Requires session expansion state and recursion/quoting rules. Not necessary for installation capability. |
| shell functions | No | Duplicates a programming feature `.run` already provides much better. |
| `if` / `case` | No | Control-flow grammar is significant work and duplicates TypeScript. Use `.run`. |
| `for` / `while` | No | Same reason: `.run` is the intentional full programming language. |
| arrays | No | Bash-style value/expansion semantics are complex and unnecessary beside TypeScript arrays. |
| subshells `( ... )` | No | Requires execution-context cloning, cwd/environment isolation, and nested status semantics. |
| brace expansion | No | Shell convenience with little architectural value for v1. |
| exported environment variables | No | No production environment-variable authority has been defined yet. Do not fake Unix process environments. |
| heredocs | No | Parser/quoting/multiline complexity. Files and `.run` template strings cover v1 needs. |

Unsupported syntax should fail explicitly and direct the user toward `.run` when appropriate. It must not be silently misparsed.

## Explicitly postponed commands

### Useful but not necessary for v1

These may be added after the v1 contract without changing the architecture:

- `touch` — simple empty-file creation is cheap, but full timestamp semantics need a real API contract;
- `diff` — useful, but requires a chosen diff/output contract;
- `cut` / `tr` / `xargs` — useful text composition, but each brings additional option/quoting semantics;
- `which` / `type` — should wait until command resolution/PATH/registry semantics are frozen;
- interactive `less` — requires pager input/session behavior rather than a simple buffered command.

### Deferred because they need broader legitimate OS capabilities

- `kill` / `pkill` / `killall` — need production process-control authority, not merely `processes.list()`;
- `df` / `du` — need truthful storage quota/capacity and/or recursive filesystem semantics;
- `curl` / `wget` — need an explicit network/HTTP capability and security model;
- `tar` — needs binary/archive APIs and safe extraction semantics;
- `ln` — Plasmon shortcuts/resources must be modeled truthfully rather than pretending Unix inode/symlink behavior exists;
- scheduling (`at` / `crontab`) — needs persistent scheduling, authorization, execution, failure, and wake semantics.

### Deferred because they are substantial languages/applications

- `find` — recursive predicate/action mini-language;
- `sed` — stream-editing language;
- `awk` — programming language;
- `vim` / `nano` — interactive terminal applications; Plasmon already has a native text editor;
- `ssh` / `rsync` — large networking/security/protocol systems;
- `top` / `htop` — interactive live resource-monitoring applications.

### Intentionally not emulated as Linux concepts

- `sudo` / `su` — Plasmon authority/capabilities are not Unix root/user switching;
- `chmod` / `chown` — no Unix mode-bit/UID/GID security model should be fabricated;
- `ip`, `ss`, `netstat`, `ping` — raw Linux network-interface/socket/ICMP semantics do not map directly to the browser/Neutron/ICP environment;
- `journalctl` / `dmesg` — future Plasmon logging should expose native logging semantics, not fake systemd or a Linux kernel ring buffer;
- Linux-specific `uname`, `free`, `uptime` interpretations — any future system-info command must report truthful Plasmon/Neutron/runtime information.

## v1 base-system scripting acceptance

The v1 surface should be considered sufficient for a straightforward base-system installer when it can truthfully perform all of these categories:

1. inspect filesystem/package state;
2. install/remove packages through the production package authority;
3. create/copy/move/remove installation files through canonical filesystem policy;
4. generate configuration files through stdout/redirection/`tee`;
5. inspect/filter text with pipelines;
6. open resulting resources/apps where appropriate;
7. report failures through command exit status;
8. use `.run` TypeScript for conditional/idempotent orchestration that would otherwise require growing a Bash-compatible control language.

Example split:

```sh
# Simple `.cmd` provisioning steps
pkg install monaco
mkdir /Documents/Templates
cp /Packages/base/default.txt /Documents/Templates/default.txt
echo enabled=true > /Documents/Templates/settings.conf
```

For conditional/idempotent logic, use `.run`:

```ts
if (!(await os.fs.exists("/Documents/Templates/default.txt"))) {
  await os.fs.copy(
    "/Packages/base/default.txt",
    "/Documents/Templates/default.txt",
  );
}
```

That division is intentional: `.cmd` is the convenient shell; `.run` is the full programming language; `OsApi` is the durable production OS capability boundary.
